# Security

## Trust model

This program runs on the same computer and account as Codex. Telegram is a remote control channel, not a new sandbox. Anyone controlling the paired Telegram account can instruct the selected native sessions within their existing permissions. Enable Telegram two-step verification and protect the local account.

## Protect the account you pair

The intended model is trusted remote control of your own computer or server. Each installation pairs its own Telegram account and bot. Choose the connected sessions and native permissions deliberately, and protect the paired account, bot token and host. An account takeover can expose data readable by Codex, including through ordinary text replies; restricting file attachments alone does not prevent that.

- Enable Telegram **Two-Step Verification** (the cloud password) and protect its recovery email. This helps protect new logins; it does not lock an already authorized session.
- Enable a separate **Telegram app passcode**, biometric unlock where supported, and a short **auto-lock** interval. Use a strong device screen lock too. These protect access to the app/device, separately from the cloud password.
- Review **Settings > Devices / Active Sessions** and terminate sessions you do not recognize or no longer use. Do not share login codes, account QR authorizations or the bot token.
- Use the native Codex permissions appropriate to the work. Project discovery scope selects sessions, not a filesystem read sandbox. Stop the relay locally or on its host if remote access is no longer trusted; stopping the relay does not cancel work already running in Codex or recall data already sent.

See Telegram's [two-step verification guidance](https://telegram.org/faq#q-how-does-2-step-verification-work), [app passcode and auto-lock](https://telegram.org/blog/photo-editor-and-passcodes), and [stolen-device/session guidance](https://telegram.org/faq#q-my-phone-was-stolen-what-do-i-do). Settings names vary by client. These recommendations reduce account risk; they are not a guarantee against a compromised or already unlocked device.

Setup displays this trust model without adding an acknowledgement gate. This guidance does not weaken existing owner checks or native approvals, and the relay does not change Telegram account security settings on your behalf.

## Relay safeguards

- Only one numeric owner ID in its matching private chat is accepted. Groups and other senders are rejected before journaling or creating per-sender work.
- Session scope is chosen locally. Selected-project mode is the default for setup and legacy configurations; paths are resolved before containment checks. Explicit `sessions scope all` or `setup --scope all` opts into all eligible loaded interactive sessions, including future projects and older sessions retained by the daemon. Ignored sessions and ephemeral contexts stay excluded. Subagents have no independent topic or direct input; supported approvals from verified spawned descendants can reach an attached root's topic. Scope cannot be changed through Telegram.
- The relay supplies no sandbox, network, approval-policy, model, instruction or working-directory overrides to native resume/start/steer calls.
- Approvals require an explicit pending native request. Host async questions use normal native user input, never fabricated approval responses. Current directory eligibility is rechecked before answering (root containment in selected mode, existing absolute directory in automatic mode); resolution, duplicate clicks and cross-topic clicks invalidate/reject controls.
- Subagent approval routing checks matching native parent/spawn metadata, every ancestor's directory and ignored status, and the attached root binding. Traversal is bounded and rejects cycles, unloaded contexts and interactive forks. Cards show the agent name and full ID; replies retain the child's original pending RPC identity. The full route and destination are rechecked at click time. Child topics, direct model input, commentary and question mirroring are not enabled by this support.
- Topic recovery commands accept only the paired owner, reject occupied topics and ignored/out-of-root sessions, and never submit native input. Unknown creation results require owner-directed binding or retry; they are not automatically replayed. Recovered topics retire old pending approval controls.
- `/model` permits the paired owner to change only the attached topic's model, reasoning effort and service tier for following requests. Controls are bound to the exact message, topic, connection and live session route; they expire after ten minutes and are consumed before writing. The native catalog is checked again before applying. These choices can affect usage costs; unknown outcomes do not authorize retries. No global configuration or native permission settings are changed.
- `/view` (dev) changes only the relay-wide presentation preference for following turns. Widgets use a fixed template with text-only native labels, private message state, no shared/public session data and no widget-origin queries. Raw commands/arguments, tool output and reasoning are excluded. Questions and approvals retain their existing route and controls. Widget turns persist an ordered result plan of text widgets, native rich tables and optional generated HTML documents. Generated table documents are escaped, static reply data uploaded from memory; they do not read local source files or change local-file export opt-in. Rich-format rejection converts only its unsent table part to HTML; unknown widget/rich/file POSTs are not replayed and may produce one plain canonical backup. Table-only results use the same completed-last-receipt authority as widget-first replies. A fixed reader renders safely serialized text/entities through textContent; raw model HTML/JS is never active. Content is private in immutable message HTML, not shared/public data. Local pages honor font/theme/safe-area changes and stay inside the 600px client cap. New Text version, legacy Full answer and activity Current step controls only read saved text. They require the paired owner, private chat, exact message/topic and unchanged eligible binding, and never submit native input. Text version and legacy Full answer require the relay/local state; the complete result documents and local paging work offline. Activity More/Less reveals already-loaded progress. Each result part needs a positive receipt; startup resumes only confirmed-unsent suffixes, never an unknown POST. Unknown initial sends retain a durable admission identity and are never replayed; result cards fall back to text when their delivery fails. A full unresolved-card queue pauses new cards instead of discarding uncertain receipts. Widgets grant no new native permission and expose no stop/shell endpoint.
- `/permissions` (main/dev after v0.1.19) lets that owner explicitly change the attached root session's permission profile or approval reviewer through native `thread/settings/update`. Opening the menu does not write settings. Full Access requires a separate warning/confirmation; custom profiles require confirmation with the native description. Full Access can allow local command execution outside the project and network access without approval prompts. The live catalog, managed requirements and session settings are checked before applying; Codex remains authoritative. Standard menu choices apply the native CLI profile/policy/reviewer tuple explicitly; Ask for approval and Approve for me share workspace access but select user versus automatic review. Custom profiles preserve policy/reviewer. Current markers compare the whole tuple. Controls expire, bind to the original message/topic/session and retire before writing. Uncertain writes are never replayed automatically. Changes affect subsequent requests, not an already pending approval or active turn, other sessions or global configuration.
- `/clear` (dev) explicitly creates one empty native conversation in the current topic and cwd. Old native/Telegram history and files are preserved; an open terminal stays on the old session. Idle or verified non-archived unloaded state, pending controls/deliveries, scope and exact binding are checked before creation and handoff. Unloaded admission validates exact identity/cwd, interactive source, persistent root metadata and terminal history without resuming the old client. A concrete saved baseline cannot pass with missing terminal history; baseline changes across question checks are rejected. Unknown starts are reconciled without replay; definite rejections unlock the original route. Routing replacement and retirement are atomic. Old settings/approval controls cannot mutate the new session; cached Full answer reads alone may follow the recorded same-topic/project lineage. New sessions inherit project defaults without model/permission overrides.
- Direct shell execution and automatic filesystem artifact discovery are absent. Owner-uploaded files are downloaded only after attachment/root checks. Downloads pin the official HTTPS host, reject redirects and traversal, cap streamed bytes, and never expose token URLs to Codex. Files use exclusive random cache paths and are never automatically executed or unpacked.
- Windows requires a native executable; `.cmd` and `.bat` wrappers are rejected.
- Bot tokens stay outside the repository, are not passed on the command line, are stripped from Telegram error text, and Telegram-token environment variables are removed from native child processes.
- Configuration uses owner-only POSIX modes; setup and start replace Windows access rules on the private directory, known state/credential files and downloaded attachments with verified current-user grants, removing broad explicit grants too. Local administrators can still access local data. Encrypted storage is not provided.

## Outgoing files (v0.1.17)

File export is off by default and requires one local `files enable` per installation. There is no Telegram command to enable it and no extra per-file relay approval after enabling. `files disable` revokes pending/new exports, but cannot recall bytes already sent or an upload in flight. A shell-capable agent running as the same OS account can modify local preferences; local opt-in is an installation control, not an independent security sandbox.

The producer command reads preferences and writes to a private SQLite queue without reading `bot.token`. The running relay rechecks the paired owner, current session, live working directory, project eligibility, ignored IDs and exact topic before uploading. The caller cannot supply a destination chat. Source files must be nonempty regular files inside that session project, outside relay private data. Symlinks/junctions, hard links, UNC paths, special files and Windows alternate streams are rejected. These are accident-prevention controls: an agent can still copy readable secrets into a permitted project file, and text replies already provide another data path. Never describe this feature as confidential-data classification or confinement against a compromised OS account.

Uploads use only the official Telegram HTTPS endpoint with redirects disabled. The 49,000,000-byte file limit, 16-request/200 MB snapshot queue, ten-minute unsent expiry and one-upload worker bound resource use. Snapshot hashes bind uploads to the queued bytes; successful receipts are retained for seven days, uncertain receipts for inspection. Interrupted `sending` jobs become uncertain, not pending. Only a definitive Telegram rate-limit rejection can schedule an automatic retry; timeouts, aborts, malformed receipts and other ambiguous outcomes do not. `/status` includes uncertain file deliveries. Private snapshot contents are removed after terminal outcomes; failed deletions block further file processing until cleanup succeeds. Telegram copies and local/Telegram backups are outside this retention policy.

## Delivery and approvals

Timeouts do not prove that an operation failed. The relay records uncertain native writes and outgoing messages and does not blindly replay them. A stale button is not an authorization for another request. After an outage, inspect the native terminal before retrying an instruction.

Development approval receipts persist independently of connection-scoped callback tokens. A replay must match the method, typed native RPC ID and complete request parameters; matching visible command text alone cannot authorize reuse. Known cards receive fresh controls only after live route checks. Unknown send outcomes never trigger an automatic replacement. A decision is durably consumed before writing to Codex, including across process restart and topic recovery; an uncertain response cannot rearm it. Unsent cards are held after restart until native replay verifies liveness. Legacy cards without this identity cannot be adopted by text.

Approvals that existed before attachment may not be replayed by Codex. Some native requests may be routed only to another owning client. Those requests must be answered in the terminal; the relay never auto-accepts them to compensate. Unsupported request payloads require the terminal. Long supported approvals use numbered parts with collapsed review blocks; decision controls appear only after every part has a confirmed receipt. Long embedded command scripts, quoted reason context and duplicated code strings in proposed execution-policy amendments may use visibly abbreviated previews. Code-heavy approval previews use at most six code lines in a compact ordinary message; repeated policy code may refer to the command preview. Ordinary command arguments remain complete. The warning states that the button approves the complete original command available in Codex, including omitted code. Canonical identity and native decisions always use the original request; proposed file changes and requested permissions remain complete. Unknown send outcomes are not automatically retried. Telegram messages are cloud messages, not secret chats: do not answer sensitive/password questions there.

State stores delivery text and topic metadata, so protect backups like credentials. Successfully handled records are pruned after seven days, except approval receipts whose request is still pending or whose submitted decision has not yet been resolved; these remain to prevent duplicate cards or decisions. Resolved approval records return to normal pruning. Full widget-answer text, message receipts and deduplication keys are retained separately from the delivery queue so old Full answer buttons remain usable; this private archive holds at most 10,000 answers and is not automatically pruned. At capacity new results use ordinary text. Removing local state also removes this archive. Uncertain records remain for inspection. Incoming attachments use a private 200 MiB cache, with seven-day expiry cleaned at the next upload. Files may remain referenced in the native transcript after expiry; backups and Telegram copies are outside this retention policy. Image decoding is delegated to native Codex. Audio/video transcription is not performed. Host-question journal inspection uses bounded buffers and is restricted to the native sessions directory; known unanswered questions retain their recovery start across reconnects. Partial answer drafts are stored privately for up to seven days and require matching stable request/question identities. Interrupted host-answer reservations become uncertain on startup and never authorize replay. Unrelated tool output and internal reasoning are not forwarded.

User-selected project code and Codex tools remain subject to the native harness's security model.

## Reporting

Do not put tokens, private conversations, real session histories or private filesystem contents in GitHub issues. Share the relay version, Codex version, OS and affected code paths. Use GitHub private vulnerability reporting if available. Otherwise, open a minimal issue requesting a private contact route, without credentials, exploit details or user data. Coordinate a fix before publishing sensitive evidence. No automatic vulnerability-report publishing is implemented.
