## Доступность и API

**Это уже не только beta:** официальный Bot API опубликовал 10.4 от 9 ноября 2026. Production ограничен личными чатами; сообщения с виджетами защищены от пересылки. `sendWidget` поддерживает `message_thread_id`, включая топики личного чата бота. Inline-отправка в production пока недоступна, `copyMessage` для виджетов запрещён. [Bot API 10.4](https://core.telegram.org/bots/api#november-9-2026), [sendWidget](https://core.telegram.org/bots/api#sendwidget).

Точные методы: `sendWidget`, `sendSharedWidget`, `editMessageWidgetData`, `editSharedWidgetData`, `answerWidgetQuery`; метода `editWidget` нет. Начальный `sendWidget` принимает `html`, `chat_data`, `public_data`, `caption`, `allow_queries`, `is_shared` и обычную клавиатуру. HTML — до 32768 UTF-8 байт, zlib — до 4096; каждое состояние — до 1024 байт. `WidgetQuery` содержит `from`, `chat`, `message_id`, `chat_instance`, `type`, `data`, но не ID топика. Запрос — 1–64 байта; ответ — до 1024 байт и за 15 секунд. Сам ответ не сохраняет состояние: нужен отдельный edit. [Методы и поля](https://core.telegram.org/bots/api#widgetquery), [ответ](https://core.telegram.org/bots/api#answerwidgetquery), [изменение состояния](https://core.telegram.org/bots/api#editmessagewidgetdata).

## Что означает sandbox-спецификация

Документ `tgw-format.md` сохраняет результаты beta-проверок 28 октября: `https://api.telegram.org/beta/bot<token>/test/<method>`. Это историческая квалификация протокола, а не требование переключить production-релей на beta/test. При расхождении применимости приоритет имеет опубликованный production Bot API. [Beta-раздел](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/tgw-format.md#the-bot-api-104).

HTML после отправки неизменяем: новая разметка требует новой карточки. Меняются только данные. Caption нужен для поиска, списка чатов и клиентов, не отображающих виджет. Старые клиенты показывают unsupported media с caption; само наличие серверного метода не доказывает поддержку конкретной установленной версией клиента. Документированный beta-контроль также обнаруживал `message is not modified` при неизменившемся состоянии — это можно считать успешным idempotent edit, но запрос всё равно нужно ответить. [Формат, caption и клиенты](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/tgw-format.md).

## Runtime и обновления

Это небольшой HTML/CSS/JS-виджет внутри сообщения, не обычная веб-страница. Клиент Telegram предоставляет runtime: собственному боту не требуется встраивать клиентский sandbox или разворачивать отдельный сайт. В виджете нет сетевых fetch/WebSocket, клавиатуры и текстового ввода; доступны ограниченный DOM, кнопки, темы и canvas. Поэтому текстовый ввод остаётся в переписке. Нужен маленький статический шаблон без React, внешних ресурсов и библиотек. [Официальный профиль авторинга](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/widget-runtime-profile.md).

`TelegramWidget.chatData` — состояние конкретного сообщения; `publicData` — переносимое/общее состояние. Изменения приходят через `chatDataChanged`/`publicDataChanged`; только бот сохраняет их. `TelegramWidget.request(...)` вызывается по нажатию и может отказать с `NOT_ALLOWED`, `BUSY`, `RATE_LIMITED`, `TIMEOUT`, `FAILED`, `INVALID_ANSWER` — интерфейс должен снимать «ожидание» и показывать ошибку. Локальное хранилище — на сообщение и устройство, не источник истины для бота. [SDK и runtime](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/sdk-v1.md).

`watchPublicData()` нужен для общих виджетов: клиент опрашивает общее состояние видимой карточки с периодом сервера, обычно 30 секунд, минимум 5. Для нашего owner-only private-чата предпочтительнее **необщий** виджет и обычные edits конкретного сообщения. Нельзя рассчитывать на постоянные фоновые запросы: спецификация требует соответствующего серверного флага, а в описанных beta-пробах его не получали. Для защиты от устаревшего результата/состояния SDK рекомендует ревизии. [Shared state и background gate](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/tgw-format.md#the-widgets-state-and-requests), [SDK revision guidance](https://github.com/TelegramMessenger/widget-sandbox/blob/7a2ec35e3e7698377626e982e98e5a1161b1aac8/docs/widget-runtime-profile.md).

## Предлагаемое применение — выводы для проекта

Это архитектурные рекомендации по результатам спецификации, а не уже реализованное поведение релея.

1. Экспериментальный переключатель обычного/виджетного представления. В первой версии менять отображение прогресса; оставить окончательные ответы и полные апрувы обычными сообщениями. Они должны оставаться читаемым архивом и работать без нового клиента.
2. Одна компактная карточка на ход: состояние, прошедшее время, текущая операция, несколько последних завершённых операций, реальные шаги плана при их наличии. Не придумывать процент или общий лимит итераций, если Codex их не сообщает.
3. Статический шаблон + небольшой `chat_data` JSON с ревизией, статусом, временем и короткими строками. Передавать строки Codex как текст, не HTML. Из-за лимита 1024 байта полные команды, диффы, ответы, исходные пути и логи в состояние не помещать.
4. Сохранять в SQLite маршрут `(chat_id, message_id) → session/turn/topic/generation/templateVersion`, подтверждённую отправку и последнюю ревизию. Топик из widget query не приходит. Нельзя выбирать сессию по произвольному `data` или видимому имени.
5. Для действий принять только официальный envelope с `from.id == owner`, исходным private chat/message и сохранённым маршрутом; дополнительно проверить актуальность binding и turn. Начать с безопасных действий «открыть текущий результат»/«обновить». `shared_widget_query` и inline origins отклонять: они не нужны приватному сценарию.
6. Если добавлять Stop, это отдельный запрос остановки **точного текущего native turn**. Он не закрывает терминал и не завершает daemon. Повторный/устаревший клик не останавливает новый ход. Виджет показывает `Stopping…` до реального native подтверждения, не имитирует завершение.
7. Обновления объединять, не отправлять каждый токен; сохранять финальное состояние, иметь приоритетные каналы для вопросов и апрувов. Не повторять неопределённую отправку карточки; неоднозначный исход подчинить существующей доставочной политике проекта.
8. Не помещать приватную информацию в `public_data` и не создавать shared objects для сессионного dashboard. Скрытый блок или отрисовка по `viewer` не делает полученные данные секретными. Авторизация всегда на стороне бота.

## Что проверить до реализации и включения

- Реальный production `sendWidget` в отдельном owner-topic и в разных клиентах: отображение, caption/fallback, тема, размер, текст и кнопки. Не обещать совместимость по одному screenshot.
- Push-обновления `chat_data`, старые/дублированные query, ответ в 15 секунд, потерю send/edit ответа, отсутствие интернета, перезапуск релея и подмену binding.
- Разметку: обе byte-size границы, бюджет состояния с Unicode, контраст/обрезание, ограниченный DOM и runtime harness. Целевой zlib размер разумно держать ниже жёстких 4096 байт с запасом.
- Отключение режима возвращает обычные сообщения без повторного запуска Codex и без потери финальных ответов/апрувов.

На этом этапе не выполнялись live Telegram/API пробы. Идентичность последнего upstream commit, опубликованная доступность API и ограничения протокола проверены; клиентский rollout и фактический UX остаются отдельной приёмкой.
