# Architecture and compatibility

## Interface language

Relay-generated controls, notices, approval-preview warnings and scratch-workspace labels use English consistently, independently of Telegram's app language. The command list has one English description per command, shared by `/help` and startup registration. Startup overwrites both the default owner-chat scope and the legacy Russian owner-chat scope with that same list, migrating existing installations without resetting pairing or permissions. Native/user text is not translated. Already persisted message/approval bodies keep their original text and delivery identity.

## Modules

- `codex.ts`: native executable, raw proxy WebSocket handshake, JSON-RPC correlation, pending-request lifecycle and native session discovery. The transport never falls back to a new daemon and never shells out through cmd.exe.
- `bridge.ts`: project/topic bindings, owner authentication, completion filtering, input routing, questions and explicit one-time approvals. It does not own native sandbox policy.
- `subagents.ts`: bounded live ancestry checks that route spawned descendants' approvals to an attached interactive root while retaining the executing child's identity.
- `model-picker.ts`: fresh native model catalogs and two-screen, topic-scoped model/reasoning/speed selection; one explicit choice changes subsequent requests without starting a turn.
- `limits.ts`: bounded account-quota formatting with dynamic windows/groups, explicit unavailable values, credits, spending restrictions and timezone-labelled reset dates. Owner-authorized `/limits` reads `account/rateLimits/read` with an eight-second timeout through the existing client, before topic attachment checks; errors are contained within the read command. Multi-bucket snapshots take precedence over the legacy single bucket. Backend restriction flags and expired timestamps cannot be inferred away from a percentage. No new cache, polling, schema migration or model turn is introduced.
- `async-questions.ts`: streaming recovery of host question/answer records omitted by App Server, using 1 MiB read chunks and a 256 KiB record bound. Each source snapshot is scanned completely before publishing questions so later answer records can invalidate them. Initial recovery starts at the latest selected turn. Durable host_watch timestamps extend recovery for previously observed unanswered questions across later turns/reconnects; unrelated tools and internal reasoning are not forwarded. Locally accepted/uncertain call IDs are excluded before applying reader capacity. Answers use ordinary native user input; unavailable journal sources produce terminal notices. Journal size alone is not evidence of missed questions.
- `attachments.ts`: authenticated incoming file preparation, private cache quotas/retention, detected image input and bounded UTF-8 excerpts. It never executes or unpacks uploads.
- `topics.ts`: durable topic creation and repair, ambiguous-result handling, rate-limit scheduling and owner-directed binding/retry. It never changes native execution policy or starts a turn.
- `telegram.ts`: fixed official HTTPS endpoint, bounded messages, request timeouts, outgoing throttling and a durable outbox consumer.
- `files.ts`: non-secret local export producer, bounded private snapshots, durable receipts and a separate single-upload consumer.
- `drafts.ts`: bounded ephemeral assistant previews, shared chat pacing, fair topic scheduling, rich/text fallback and cancellation. It never stores or replaces a permanent answer.
- `widgets.ts` / `widget-types.ts`: per-session view selection, turn-latched activity summaries and safe native recovery; no native mutations. `widget-template.ts`: fixed mini-HTML using Telegram theme, text and safe-area tokens, with textContent-only data rendering.
- `commands.ts`: one English command catalog for `/help` and Telegram menus, including the legacy Russian scope. Setup and start synchronize only `BotCommandScopeChat` for the owner; broader scopes are untouched. Start runs synchronization separately from native attachment and polling; failures are nonfatal and retried next start. `doctor` never registers commands. Menus do not authorize inputs: Bridge still rejects foreign senders, non-private chats and sender/chat mismatches before command parsing or payload storage.
- `format.ts`: CommonMark/GFM parsing into Telegram text entities, safe external links and UTF-16-aware splitting. Raw HTML is displayed literally; code never nests inside formatting entities.
- `state.ts`: SQLite bindings, update IDs, delivery status and a local singleton lock. Unknown users' payloads are not stored.
- `config.ts` / `cli.ts`: local pairing, secret input, project selection, user-profile state and process lifecycle, verified Windows ACL protection, and missing-executable recovery after a read-only native compatibility check.

Native I/O and Telegram I/O have real adapters and test adapters. Most behaviour is exercised through Bridge's request/event/update interface; a separate integration fixture tests actual WebSocket-over-pipes framing.

## Native sessions

### New conversation creation

`NewSessions` owns the `/new` picker and durable SQLite `new_sessions` workflow. Authorization remains in `Bridge.update` before allocation. Legacy configurations receive automatic in-memory defaults: enabled creation, selected roots plus known connected projects within discovery scope, and a separate conversations directory next to relay data (falling back to `~/Codex/Conversations` inside Git checkouts). `/new` prepares that directory lazily; config reads and doctor create no workspace and rewrite no configuration. Explicit custom settings/disable are preserved. Discovery scope `all` permits known connected projects, not arbitrary Telegram filesystem paths. Canonical paths are rechecked before writes; scratch uses one retained operation-UUID child, outside private data, Codex home and Git repositories. Selected-scope guards admit owned scratch consistently in discovery, root/subagent routing, models, outbox, drafts and both file-export phases. Display labels never replace actual security paths.

The journal precedes filesystem, Telegram and native writes. New menu operations set `topicFirst`; unstarted legacy selecting/preparing operations also opt in. Already-started legacy operations retain compatible recovery. Within `preparing`, topicState records creating/retry/failed/uncertain/ready and a monotonic topicAttempt. A positive createForumTopic receipt or explicit owner selection of an unbound topic persists targetTopic before any native start. Unknown/interrupted topic requests pause with no native session; only proven pre-connect errors and429 retry automatically. Attempt-scoped owner controls can retry, cancel, or reserve an existing topic for `/bind`; they never dispatch model work. Once confirmed, stages continue through starting/known/persisted/topic/ready. A startup starting becomes uncertain. Native creation sends only cwd, ephemeral:false and the operation marker as threadSource. The returned ID is saved before validation; naming materializes empty history and turns/list must succeed before attachment. The confirmed topic is installed and renamed for the real native ID, without another createForumTopic call. No synthetic prompt or policy override is used.

`thread/started` can record the exact ID before a lost start response. Otherwise unknown starts use bounded metadata scans for the exact marker and cwd; missing or incomplete results stay uncertain and never repeat start. The marker is correlation metadata, not authority or server idempotency. Confirmed Telegram topic IDs survive native start/name/resume uncertainty. Older native-first topic failures use the existing Topics recovery path. Owner recovery may resume an unloaded exact owned ID only after active-history, identity and workspace checks; ordinary foreign session readiness is unchanged. The origin binding/questions stay untouched, and the new binding receives baseline - before its first task.

Codex 0.166.0 omits even named empty threads from ordinary `thread/list`. For known IDs, `nonArchivedThread` verifies the real persisted `.jsonl` path under active `CODEX_HOME/sessions`; `archived_sessions` means do not resume. Other/unreadable locations fail closed. This version-sensitive check has an opt-in native qualification test. Ready owned sessions can resume after relay/native restarts within remaining capacity. One unavailable saved session produces a deduplicated notice without stopping healthy sessions. Ordinary foreign sessions retain loaded-only discovery and first-message protection.

`new enable` optionally overrides creation locations; native project loading may itself initialize trust. The relay adds no custom trust parser or trust-write RPC. General conversations retain global instructions, memory, skills and plugins; separate directories isolate work products, not all machine access. No scratch auto-cleanup exists. Native-daemon availability and connected-loop Telegram polling remain prerequisites; daemon management and offline polling are separate features.

### Existing session discovery

The relay asks the existing daemon for loaded thread IDs, reads metadata and selects root interactive sessions (`cli`, `vscode`, `appServer`) for individual topics. Ephemeral and not-yet-materialized sessions are excluded. Spawned subagents have no individual topics or direct input; their supported approvals can reach a verified, attached root as described below. Discovery runs approximately every five seconds. Selected-project mode is the default for setup and legacy configurations. Explicit local `sessions scope all` or `setup --scope all` includes all eligible interactive session directories, including future projects, without changing native execution permissions. Ignored IDs remain excluded in both modes. Input, outgoing events, approval controls and topic recovery use the same scope check; changing scope requires a relay restart and cannot be requested remotely.

Development discovery scans loaded IDs in batches with at most eight concurrent metadata reads. The 64-session limit applies after native eligibility, configured project scope and ignored-ID filtering; excluded subagents/projects do not consume it. A 65th eligible session emits a console warning and a durable Telegram attention notice. Journal scans are serialized per session so discovery and button-liveness checks cannot corrupt each other's snapshot. Periodic discovery runs beside input polling, with one scan at a time; shutdown awaits that scan after closing its native transport. Initial attachment still completes before normal input polling begins.

If metadata, resume or history fails for one session, discovery continues for healthy sessions and retries the unavailable session later. Sessions missing from a successful discovery are detached locally. Uncertain native transport failures propagate to the connection loop instead of being treated as local session failures.

Before creating/replacing a topic or attaching an unattached session, the relay checks summarized history. A nonempty rollout path is insufficient: Codex can advertise a reserved path before its first input. Only the exact native pre-first-message history rejection becomes `FirstMessageRequiredError`; a successful empty history remains valid, and other failures retain their normal handling. Waiting creates no topic or unavailable warning, including after reconnect. Saved-topic text/media diagnostics and manual recovery explain the first local message requirement. Bindings still precede attachment so replayed approvals can route. If this connection observed the waiting state, its eventual baseline preserves the first completed answer even when the session was opened before the relay. An unseen completion predating the connection retains the ordinary no-history-import boundary. See [research and reproduction](research/first-message-attachment-2026-11-05.md).

Attachment calls `thread/resume` with only `threadId` and `excludeTurns`. A Telegram instruction calls `turn/start` with only its thread ID and text/media input, or `turn/steer` with the expected active turn ID. This intentionally inherits native policy. A rejected or ambiguous steer is never reinterpreted as permission to start another turn.

On first attachment, existing completed history is used only as a baseline. It is not posted to Telegram. History requests use display summaries, excluding large historical tool outputs. Reconnection catches up at most the ten most recent turns for each saved binding. A long outage can therefore leave older missed completions available only in the native terminal. This is a bounded recovery window, not a full transcript mirror.

### Subagent approvals

After root attachment, discovery inspects loaded descendants and subscribes to up to 128 eligible agents. More eligible agents produce a terminal-check notice. Each route reads current native metadata with a one-second timeout per read and visits at most 16 contexts. Every child must have matching `parentThreadId` and `source.subAgent.thread_spawn.parent_thread_id`, with `canAcceptDirectInput: false`. The chain must reach an attached interactive root whose saved directory matches its current directory. Cycles, missing ancestors, unloaded or ephemeral contexts, ignored IDs and disallowed directories are rejected throughout the chain. Directory, display name and short ID never establish parentage.

Each eligible child is resumed without policy overrides so Codex can replay its own pending requests; resuming only the parent does not recover descendant approvals. Readiness is checked first. A reconnect starts fresh subscriptions; retiring a root topic's prompt controls also invalidates its descendant subscriptions so topic recovery obtains fresh child controls. No child binding or model turn is created.

Supported child command, file-change and permission approvals use the root's destination but retain their original RPC/thread/turn/item identity. Cards include the agent name and full ID. Owner/topic checks, request liveness, current ancestry and destination are checked again before a single response to the child request. File-change caches and terminal-only notice keys use the origin child. Terminal resolution and child completion retire only matching child controls; parent completion does not retire them. Other child requests receive a terminal-only notice when a destination can be verified. Child conversation text and host-question journals are not mirrored. [Native contracts, reproduction and verification](research/subagent-approvals-2026-11-05.md).

### Session model selection

`/model` in an attached root topic reads `thread/read` and all `model/list` pages. Screen one lists current catalog models and marks the configured model when available; screen two offers complete reasoning/service-tier combinations. Each combination applies immediately, without Refresh/Apply buttons. Known effort labels are presentation only; opaque model, effort and tier IDs come from Codex, so newly advertised values do not require a relay release. Only `serviceTiers[].id` supplies additional speed tiers; deprecated `additionalSpeedTiers` display names are not guessed into native IDs. Ordinary processing uses the protocol's explicit `default` tier, rather than inheriting a prior Fast override. Long lists have pages; reads stop with an explicit error at 512 entries or invalid/repeating cursors rather than silently using a partial catalog.

Each initial menu uses a cancellable `prompt/model/` outbox entry. Controls are unguessable, bound to its confirmed message ID, topic and current connection, and rotated between screens/pages. Only the latest menu per session is active; menus expire after ten minutes, with at most 64 open menus. The existing owner/private-chat authorization runs before menu allocation. Live attachment, binding/directory, ignored status and session readiness are rechecked after reads, including immediately before applying. The catalog is fetched again before the write so a removed combination cannot silently substitute another one.

A selected combination calls `thread/settings/update` with only `threadId`, `model`, optional `effort` and `serviceTier`. These are the explicit owner-selected exception to otherwise inherited model settings. It creates no session/turn, never steers or interrupts the active turn, changes no global config and supplies no permission overrides. Codex owns persistence for subsequent requests in that native session, including requests from other clients. Acknowledgement confirms the settings update, not model entitlement or a successful inference; later native errors remain authoritative. Success text says the settings are saved for all following requests, with an extra notice when a turn is already active.

Controls are consumed before the native write; an ambiguous acknowledgement closes the menu without automatic replay. Startup cancels unsent old menus and a fresh connection rejects their old callbacks. Queue admission, project-scope cancellation and owner checks remain shared with other prompts. Telegram edit failure can produce a separate durable outcome notice, but never another native write. There is no fallback through a fake prompt or global configuration write when the native setter is unavailable.

Protocol evidence: the [official App Server documentation](https://learn.chatgpt.com/docs/app-server) defines `model/list` and reasoning options, and identifies `default` as standard processing. `codex-cli 0.166.0 app-server generate-json-schema --experimental` additionally confirms `Model.serviceTiers`, current `Thread.model/reasoningEffort` and the experimental `ThreadSettingsUpdateParams` fields above. The public page does not currently describe that setter; compatibility beyond the qualified local schema requires acceptance testing. The actual daemon catalog was read without changing live settings. [Verification](verification.md).

### Activity widgets

`/view` is default-Classic and scoped to the attached root. Menu choices or direct arguments save only a presentation preference. A native turn start/recovery captures that preference; later changes do not switch a running turn's representation. The quick event path observes turn/item lifecycle and structured plan events, excludes user/agent message bodies, reasoning and arbitrary tool payloads, and keeps bounded safe tool categories. Existing answers/questions/approvals stay on their ordinary delivery paths. Only root-turn prompts affect the waiting status; child approvals keep their existing separate cards.

`widget_cards` is a durable desired-state queue consumed by `Outbox.flushWidget` in the existing sender. Generation and exact binding/cwd checks precede sends. Each record stores a safe snapshot, immutable turn admission identity, receipt, revision and send/edit state. Initial sends are delayed one second and suppressed for quick finished turns. Edits coalesce with a 2.5-second minimum; a single worker prevents overlapping calls. The shared preview budget alternates widget work with answer drafts; permanent output takes priority. Widget JavaScript rejects a lower revision, renders values as text, updates a local timer and responds to native theme/text changes. Chat data targets 900 UTF-8 bytes, including JSON escaping; mini-HTML is tested below 32768 source/4096 compressed bytes.

Interrupted initial sends become uncertain on startup. `everUncertain` survives retirement and is never pruned. Live and unsettled final receipts also survive admission pressure. Only settled history is evicted; at 512 protected records admission pauses with a notice. An edit targets a known message and can retry a complete snapshot; it cannot create another widget. Reconnect gates the queue on the new bridge generation and fresh native route, hydrates known activity outcomes, preserves already observed terminal snapshots/task context even outside bounded history, and hides unavailable structured-plan counters until a fresh plan notification. Late item/plan events cannot open new cards without turn start/recovery.

The widget is non-shared, with private `chat_data`, no `public_data` and `allow_queries=false`. An ordinary inline fallback button uses the existing owner/private-chat gate and the saved message/topic route. No widget-query polling, Stop, limits dashboard, arbitrary generated HTML, Mini App or new server is introduced. Production API/client compatibility and official runtime qualification are documented in [verification](verification.md).

### Session permission selection

`PermissionPicker` exposes two operations: open a session menu and handle a scoped callback. `CodexClient` retains actual permission settings from the existing `thread/resume` response and subsequent `thread/settings/updated` events. There is no additional resume or invented settings-read endpoint on menu open. Opening and every selection read all `permissionProfile/list` pages for the current cwd, `configRequirements/read` and the thread's `experimentalFeature/list`. Failed/malformed/incomplete reads fail closed. Native profile IDs are opaque; built-in IDs only supply labels and native preset approval policies. Full Access maps to `never`; read-only/workspace map to `on-request`; custom profiles preserve the existing approval policy. Reviewer changes are separate and preserve the profile/sandbox. Native validation remains authoritative, including model-dependent managed restrictions.

Full Access and custom profiles require a distinct confirmation screen. Tokens rotate on every screen, expire after ten minutes and are bound to the confirmed Telegram message, topic, connection, attached root and cwd. Confirmation includes a signature of the cached native profile, complete sandbox policy, approval policy, reviewer and model/provider; local changes invalidate it. Profiles and eligibility are rechecked before applying. The setter accepts only explicit `permissions`, `approvalPolicy` and/or `approvalsReviewer` fields. It requires the matching applied-settings notification after native acknowledgement before reporting success. The callback is consumed before writing; timeout, missing notification or disconnect does not trigger replay. No settings, model turn, pending approval answer or global config write occurs during menu reads/cancellation.

Qualified against Codex CLI 0.166.0's experimental schema and a real isolated App Server, using the [official permission-profile protocol](https://learn.chatgpt.com/docs/app-server) and [native auto-review behavior](https://learn.chatgpt.com/docs/sandboxing/auto-review). Older native APIs fail with an unavailable-menu notice rather than falling back to a synthetic prompt. [Verification](verification.md).

## Telegram identity and topics

Setup checks getMe/private topics and refuses existing webhooks. It accepts a private `/start RANDOM_CODE` generated locally and saves the sender's ID. Runtime requires the same sender ID and private chat ID. One session maps to one topic through persisted native thread IDs and Telegram topic IDs; visible names never participate in routing or matching.

Topic names use a static project/short-ID format. The obsolete topicTitleMode setting is removed on startup. Existing saved status titles are reconciled to static names without recreating topics; subsequent native status changes do not rename them. Rename errors retain bounded backoff and normal missing-topic recovery.

Topic creation has a durable operation record written before the request. Interrupted `creating` records become `uncertain` at startup. Unknown network/server outcomes are never automatically retried; definite rejections require explicit repair, and 429 responses defer retries until `retry_after`. An owner can bind an already created topic with `/bind ID` from that private topic or explicitly reattempt creation with `/repair ID`. Recovery rejects ambiguous session prefixes, ignored/out-of-root sessions, occupied topics and concurrent creation. Healthy bindings are not silently replaced.

A binding is durable routing metadata, not proof of native liveness. `/sessions` exposes saved topic IDs separately from relay attachment. With no topic operation pending, `/bind ID` and `/repair ID` in the saved topic retry normal loaded-session discovery and attachment; another topic receives the saved destination without changing it. Detached-session diagnostics distinguish an unloaded/ineligible native session, a loaded session whose attachment failed, ignored/out-of-scope sessions and an unavailable native connection. Unloaded sessions must first be resumed locally; these commands never manufacture a replacement native session or submit a turn. See [incident research and terminal-exit feasibility](research/topic-attachment-and-terminal-exit-2026-11-04.md).

A definite missing-topic error blocks that topic's unsent output while other topics continue. A replacement is created for a loaded session through the same journaled path. Installation atomically changes the binding, transfers blocked/pending non-prompt output and retires old pending prompt controls. Already sent or ambiguous deliveries are not replayed. The native session is reattached without policy overrides; any replayed prompts get fresh topic-scoped controls. Deleting a topic is therefore not an instruction to disable its loaded session; use `sessions ignore` first when removing it permanently.

Startup checks `getMe` and `getWebhookInfo` before opening the native connection or starting delivery workers. Temporary network/5xx failures retry these read-only checks after three seconds until success; 429 waits at least three seconds and honors a longer `retry_after`. Invalid credentials, disabled private topics and an existing webhook still stop startup. Ctrl+C retains normal process termination during this phase. Setup and doctor retain their one-shot checks.

One process consumes getUpdates. Transient network/5xx polling failures retry with exponential backoff up to 30 seconds; 429 respects Telegram's retry interval. Discovery and the native connection remain active during that backoff. Authentication and competing-consumer errors remain fatal. Sanitized console notices distinguish a polling outage and its recovery from native reconnection. The owner check happens before creating work or journaling an input. Input IDs and the polling offset are durable. A crash between sending a native request and receiving acknowledgement is marked uncertain; it is not replayed. There is no exactly-once guarantee across Telegram and native Codex.

Development finals and attention/status notices first enter the durable outbox as `deferred`, outside the 1,000-entry active admission limit. `next()` promotes them into available pending slots; attention/status notices take priority, and finals retain saved ID order. This keeps an observed final durable before Bridge advances its turn baseline, including when later turns finish or the process restarts. `/status` reports pending/blocked/deferred final answers. Ordinary commentary still has bounded admission and can be rejected under overload. Deferred final text retains the existing 40,000-unit per-message bound; unsent final records have no time-based pruning and consume private disk until sent or cancelled. Monitor the pending-final count and restore connectivity; the active limit does not cap total spool disk usage. Storage failure is still an error, not a delivery guarantee. Older versions do not process `deferred`; do not downgrade while that backlog exists.

The development sender requires the installation policy explicitly. Before selecting work it cancels disallowed pending, blocked and deferred project contexts; before each ordinary/rich network attempt it checks both the saved output directory and current binding directory. Queued project notices retain their originating thread ID even without a topic, so ignoring one session does not suppress another in the same directory. Legacy origin IDs are migrated from saved bindings/topic operations; unresolved legacy session warnings are cancelled without changing sent or uncertain outcomes. Project output with unknown topic bindings is cancelled rather than routed elsewhere. Explicit projectless owner help/status/recovery diagnostics remain available in an unbound private topic, so an owner can repair its binding. Narrowing scope or ignoring a session therefore revokes already queued output after restart; cancelled rows do not resume if scope is later expanded. Calls already in flight cannot be recalled. Sent and uncertain records retain their status, and no native instruction is repeated. General relay notices without a project remain available.

Final agent answers are buffered until turn completion. In the default `all` mode, each completed assistant commentary or partial-answer message is delivered and deduplicated by native thread/turn/item identity. In `compact` mode, only the first commentary reply after Telegram input is delivered; later commentary and background-session commentary are omitted. Tool/file/command events and internal reasoning items are never mirrored. The owner can change this durable global preference with `/mode all|compact`; it affects future messages immediately and does not import previously skipped history. Native questions and approvals carry unguessable, topic-scoped callback capabilities. Multi-question prompts rotate capabilities so an old answer button cannot answer a later question. Unknown request types and unsupported question payloads are left to the terminal. Terminal-only attention notices use persistent native identity and do not repeat for the same request across reconnects. Attaching to a waiting session alone does not emit another warning.

Interactive question cards require the native `item/tool/requestUserInput` request. Each question lists numbered options with full descriptions, one button per option, and a free-text alternative. Multiple questions are answered sequentially using their original native IDs. At most ten questions with unique IDs, ten choices per question and 18,000 serialized characters per question are supported; secret or unsupported questions stay in Codex. Ordinary assistant prose, including questions from tools that do not emit this native request, is not classified into buttons.

The local `sessions ignore/unignore` commands resolve an exact ID or a unique prefix against stored bindings using a read-only database connection. They update only local `ignoredThreadIds` preferences; the token file is not rewritten. After restart, ignored sessions are never resumed and their pending topic deliveries are cancelled without sending or changing native requests. Existing bindings/history remain for re-enabling. Closing a terminal window does not reliably remove a daemon-loaded thread, so there is no automatic Telegram topic closure or deletion.

Instructions (including steering), completed question answers and root-session approval decisions durably record that an assistant reply is awaited before writing to Codex. This captures replies arriving before the RPC result. The first commentary message in the matching turn is queued once per Telegram update, then the wait is consumed. Questions and final answers also consume the wait. Failed writes clear it, and a reconnect preserves it without replaying commentary already delivered. Child approval decisions respond to the child request without registering a child turn as an awaited root reply. No canned acceptance/decision/answer messages substitute for the assistant's words. If Codex emits no initial commentary, the next visible response is its question or final answer.

Short assistant messages use explicit Telegram entities instead of `parse_mode`: CommonMark differs from Telegram MarkdownV2. Entities use UTF-16 offsets and are clipped/rebased for each message, with at most 100 entities per chunk. Approval cards fence literal commands/diffs and escape justification text; question text stays literal. Commands containing carriage returns or invisible C0 controls (except LF/TAB) or DEL use a labelled JSON-string representation, making those characters visible and round-trippable instead of allowing CommonMark newline normalization. This changes display only, never the native request. Local file and local/private preview URLs retain their label and target as text. A definite HTTP 400 entity error retries only the rejected chunk without entities; accepted chunks are never replayed.

`rich.ts` converts assistant answers containing tables or headings into allowlisted Telegram rich blocks. Raw HTML stays literal; media references are never uploaded/fetched automatically, link validation is shared with the ordinary renderer, and automatic entity detection is disabled. Each part retains the italic project signature. Conservative budgets cap serialized rich payloads at 24000 UTF-8 bytes and 300 objects, below the documented text/block ceilings. Table rows split with repeated headers. Tables wider than 20 columns and oversized rows become complete labelled paragraphs; oversized text/code blocks split without cutting Unicode characters. Oversized formatted text blocks may lose inline styles during this text-preserving fallback. Ordinary short replies, questions and approvals keep their existing path.

Before a rich network write, the outbox persists its method/payload plan. Each successful part advances durable progress. A definite rich-format/method rejection replaces only that unaccepted part with readable text cards and persists the changed plan before sending. Missing-topic recovery resumes only unaccepted parts, including after a restart; ambiguous sends remain uncertain and are never replayed. Existing source-text limits in State.enqueue still apply: answers exceeding 40,000 UTF-16 units are shortened with an explicit terminal notice. Embedded rich buttons and raw model-supplied HTML/media are not enabled. Recipient client-version negotiation is not documented; actual client appearance remains an acceptance check.

### Pending approval replay

`approval_requests` records a canonical fingerprint of the method, typed native RPC ID and complete parameters, including originating thread/turn/item and permission context. Native replay within one daemon preserves that ID. Distinct IDs or changed proposals are independent requests even when the rendered commands match. `approval_cards` separately records each request's destination/presentation, durable outbox key and current callback owner. Reconnect replaces callback authority without changing the delivery identity or posting another known card.

A confirmed receipt permits editing the final message's inline keyboard; multipart review text stays intact. Pending unsent cards reuse their queue entry. Startup holds these cards until a live replay revalidates the route and installs fresh controls; reactivation respects the 1,000-entry active queue limit. Terminal resolution cancels held work even if no in-memory prompt exists. Pending/consumed requests retain receipts beyond the usual seven-day cleanup, while resolved records return to normal pruning. Scope cancellation includes held cards.

Long supported approvals use a persisted `sendMessage` plan with numbered parts, a stable request reference and project/task signature. Each body uses an `expandable_blockquote` entity, collapsed by default, with literal review text and no nested code/pre entities. Spoiler noise masking does not reduce message height and is not used. When an older persisted plan resumes, only its unaccepted parts have spoiler entities converted to collapsible quotations; confirmed parts are never reposted or edited. Short approvals keep their ordinary formatting. Simple heredocs and recognized inline interpreter commands (for example `node -e`, `python -c` and PowerShell `-Command`) exceeding 600 UTF-16 units or six lines use compact head/tail previews: at most four initial lines (350 units), one final line (120 units) and one omission-marker line. Their long string elements in `proposedExecpolicyAmendment` receive the same preview treatment; an exact duplicated script instead refers to the command preview. Ordinary command arguments remain complete. Explicit code/blockquote reason context uses the same abbreviation budget. Fenced reason code renders as actual code entities, with surrounding prose kept outside the block. Up to three examples (the first two and last) share a 1,000-unit excerpt budget; additional code blocks receive one omission notice. CRLF/CR reason line endings normalize only in the display copy before lexing, preserving canonical parameters. Compact code cards fit in one ordinary message with their warning and buttons, without numbering or expandable quotations; only genuinely multipart review content uses the persisted collapsible plan. Preview cards warn that the decision applies to the full original command in Codex; each multipart preview repeats that warning outside the collapsed body. Proposed file diffs and requested permissions remain complete, and registered approval cards bypass the ordinary 40,000-unit answer cap. Canonical request/card identities and native decisions still use the complete original payload. Existing persisted plans retain their text and part indices. See Telegram's [MessageEntity types](https://core.telegram.org/bots/api#messageentity) and [entity nesting rules](https://core.telegram.org/bots/api#formatting-options).

Every confirmed part checkpoints its message ID and next index before another send. One part is processed per outbox pass; a definite `429` saves its retry deadline across restarts. A definite entity rejection retries only that unaccepted part as plain text, keeping numbering. Ambiguous delivery remains uncertain without automatic resend. Pending cards are held on startup until native replay, then resume at the saved index; native resolution cancels remaining work, including in-flight delivery continuation. Long approval sends contain no decision keyboard: only after all receipts are confirmed does the bridge revalidate the live request and edit the final message to add controls. Keyboard refresh has priority over the next outbox send.

Unknown send outcomes stay uncertain across connection and process restarts. Without a known message ID the relay emits a stable terminal-required notice instead of another card. Temporary keyboard-edit failures retry against the known message with backoff. Delayed operations from a former callback owner cannot update the current receipt; its current owner reconciles late keyboard writes, while already-closed requests have controls removed. Errors for retired bindings cannot trigger recovery of a healthy replacement topic.

The native request is durably consumed before a response is written. Reconnect, restart and a recovered destination cannot rearm an uncertain decision. A still-pending request may need a new card after its topic is actually lost, because the old message belongs to the former destination. Legacy cards have no stored native identity and cannot safely be adopted by visible text, so the first replay after upgrade may create one new card. No native decision is inferred from an old button or a matching command. [Research and regression checks](research/repeated-approval-cards-2026-11-05.md).

### Live answer previews

The native client subscribes to `item/agentMessage/delta`, while command output and reasoning remain excluded. Only a known `agentMessage` start can open a preview; orphaned deltas, tools and unsupported phases cannot. Deltas accumulate synchronously outside the serialized control-event queue. At most 64 sessions retain one draft each, with a Unicode-safe 12,000-unit preview tail. This bound never replaces the authoritative completed item/turn text used by the durable outbox. Multipart rich previews display only the latest part; final delivery preserves all parts within the existing source limit.

All eligible previews use `sendRichMessageDraft` with allowlisted explicit rich blocks, including paragraph-only prefixes. Each update is a full valid snapshot; incomplete Markdown can appear literal and change layout as it becomes recognizable. Raw model Markdown is not passed to Telegram's richer HTML/media parser. A definite rich-draft rejection permits an ordinary text preview, retaining the same draft ID. A preview failure cannot mark the permanent outbox uncertain or replay a native instruction. No paid broadcast or automatic stop/interrupt controls are enabled.

Streaming defaults to on and is an owner-only persisted `/stream on|off` preference, independent of `/mode all|compact`. Eligibility is checked again before sending, including a live native directory read with a one-second timeout. Changed topic bindings, missing topics, detached/ignored sessions and disallowed directories cannot forward buffered previews. Native request processing and discovery do not await draft delivery.

One sender prioritizes permanent output and serializes preview HTTP calls with outbox sends. This prevents locally acknowledged previews from overtaking final answers; a timed-out HTTP request still has an uncertain remote outcome, so exact client ordering during network failure is not guaranteed. Draft HTTP calls time out after three seconds. Generation completion, disconnect and disabling streaming discard buffered updates; reconnects recover permanent completions, not historical token streams. Already visible drafts expire after 30 seconds or are cleared by permanent messages in that topic.

All topics share at most one draft call per second, with fair scheduling, 15-second refreshes for still-active idle drafts and server `retry_after` cooldowns. The shared budget survives native reconnects. These conservative targets respect the documented 20/5-second and 40/30-second chat-wide live-draft limits; simultaneous topics, permanent-output priority and network delays reduce the observed update frequency. They are not measured latency guarantees. [API contracts and research](research/telegram-streaming-drafts.md).

Development session output includes an italic `» project-name • session-name` signature. `thread/read.name` supplies the native title; discovery and `thread/name/updated` refresh it. A per-session event version prevents a slow discovery snapshot from overwriting a newer rename. Empty titles use the short native ID. Project context and the bounded, control-sanitized session label are captured in nullable outbox/file-job columns when queued; old records keep the old project-only form rather than acquiring a later task name. Drafts keep the label captured when they start. Ordinary/rich parts, rich fallback, model controls and file captions use the same formatter. Chunk budgets include the longer signature, and body entity offsets are shifted without overlapping its italic span. Topic names and routing IDs are independent of task labels.

The development command menu omits `/say`, `/bind` and `/repair`. `/say` is removed entirely without an alternative instruction mode; normal text retains the existing pending-question answer behavior. `/questions` republishes actionable cards only after live checks and an immediate second liveness/map check, so a concurrently resolved question is not reposted. Manual `/bind ID` and `/repair ID` remain in help. Topic-problem cards have owner-only attempt-scoped buttons, tied to the confirmed original message outside topics. A bind choice reserves one session for ten minutes on the current connection; `/bind` without arguments in the destination topic rechecks loaded-session scope/readiness and the same operation before binding. A retry choice enters the existing journaled creation path, which rotates the attempt before awaiting Telegram. No model instruction is sent by either action.

## Outgoing project files (development version)

Local `files enable` opts this installation into exports; absent/false configuration keeps them off. `send-file` uses a second SQLite connection alongside State's singleton lock, without reading the token or contacting Telegram. It verifies that the active relay lock matches the file worker's generation; old relay versions cannot silently accumulate unconsumed jobs. Routing comes from an explicit session, `CODEX_THREAD_ID`, or a unique working-directory binding. The caller cannot choose chat IDs. The worker rechecks local opt-in and native loaded/attached session eligibility immediately before sending, including unchanged directory and destination.

Each request snapshots one bounded regular project file to an exclusive 0600 cache entry and commits `preparing → pending`. Admission reserves quota transactionally before writing the snapshot. A single worker, independent of the permanent-message/draft sender and input loop, verifies snapshot identity, commits `sending`, and uses multipart `sendVideo` (MP4) or `sendDocument`. A matching owner/topic/message receipt commits `sent`. Definitive API rejection commits `rejected`, except bounded 429 cooldown retries; ambiguous transport, abort or mismatched receipt commits `uncertain`. Startup changes interrupted `sending` jobs to uncertain, and interrupted preparation to rejected. Only unsent pending jobs can resume automatically. No native turn or permission overrides are added by exporting.

The queue caps files at 49,000,000 bytes, 16 active requests and 200 MB of snapshots. Unsent jobs expire after ten minutes. Terminal snapshot bytes are removed; successful/rejected receipts deduplicate for seven days and uncertain receipts remain. At 10,000 retained receipts, admission fails rather than growing without bound. Default identity hashes owner/session/topic/project/name/content/kind/caption; explicit caller IDs must match their original fingerprint. CLI success requires `sent`; a three-minute wait ending before delivery returns code 2 with the durable request ID. A 120-second upload timeout is ambiguous and never authorizes replay. Local disabling affects requests that have not begun uploading; in-flight sends cannot be recalled. See [security](../SECURITY.md#outgoing-files-development-version).

## Initial release limits

Native executable discovery resolves Unix symlinks and known npm launchers to native platform packages without executing the launcher. Current `vendor/<triple>/bin` and older `vendor/<triple>/codex` layouts are supported, with Node package resolution covering nested/hoisted dependencies. Executable format and POSIX permissions are checked; `.cmd`/`.bat` entry points remain rejected on Windows. Private configuration/token symlinks are still rejected independently.

- Native compatibility is targeted at Codex CLI 0.166.0. App Server remains an evolving protocol. Unsupported versions should fail without spawning a replacement harness.
- No MCP server is needed to use the relay. Future MCP registration can be an optional adapter; it is not the core execution interface.
- There is no real Telegram bot exchange in automated tests. BotFather settings, user pairing and actual mobile/desktop topic UI require a live acceptance pass.
- Existing approvals from before attachment, connector elicitations, native approval routing between clients and reconnect replay depend on Codex behaviour. Use the terminal whenever the request cannot be safely identified/displayed by this client.
- Incoming attachments, opt-in outgoing project files and `/new` thread creation are supported in development; audio transcription/video decoding, server deployment and auto-start installation are not implemented.
- Native settings are inherited. The relay does not enforce a stronger sandbox than the native owner selected.
- Slow/failed Telegram deliveries are not an excuse to repeat a native instruction. Outgoing ambiguity is visible in `/status`; inspect the terminal and local state before retrying.

## Verification

`npm test` uses synthetic projects, an in-process Telegram adapter, temporary SQLite stores and an actual HTTP/WebSocket peer behind a subprocess's stdio. It does not read user conversations, start live model turns or use credentials.

`doctor` is read-only: initialize, list loaded threads and read metadata, plus getMe/getWebhookInfo if configured. It never resumes a thread, starts a model turn or changes Codex settings.
